# QE setup — conduit-api-qe

How the agentic QE workflow in this repo is set up, how to use it, and what to
do with it when the engagement ends. Written for people; everything else appqe
deploys is written for the agent.

Generated by appqe. Re-run `appqe sync` after changing `appqe.yml`.

## Prerequisites


The guardrails shell out to the `appqe` CLI and **fail closed**: if it is not
installed (or the editor can't find it), tool calls are blocked rather than
silently unguarded. Get set up:





```bash
uv tool install "appqe @ git+https://github.com/Slalom/appqe.git"   # or pipx / pip install "appqe[openapi]"
appqe --version                  # expect: 0.12.11
appqe doctor                     # verifies wiring in this project
```

If that command does not work for you, this project has not recorded how it
distributes the CLI yet - ask whoever set appqe up here for the install command
your team uses, and put it in `appqe.yml` as `install_command:` so this page
prints it for the next person.


Blocked or misbehaving? `appqe doctor` checks PATH, `APPQE_BIN`, the config/spec, and the
hook wiring for this project, with a fix printed for each.

`appqe doctor` is the quick project-only check worth running after any setup change:
it reports whether the CLI resolves, the config and spec load, the hooks are wired
for this host, and whether a coverage baseline exists.

## Using it — two surfaces

You interact with appqe in two places, and keeping them straight is what people
trip on:

### 1. In GitHub Copilot — you *drive* a workflow, the agent *runs* it

> This project is set up for **GitHub Copilot** (`default_platform: copilot` in `appqe.yml`). Driving it from a different agent means that agent's content was never deployed - `appqe doctor` says so, and `appqe sync --host <agent>` deploys it (real-time hooks on Copilot, Claude Code, Kiro and Cursor).

Select the **appqe-conduit-api-qe** agent, then describe the task (or fire a ready-made prompt).

Whichever way it starts, the agent drives a phased run through the orchestrator
— it calls `appqe start` and `appqe resume` **itself; you never type those** —
and stops at the approval gates for you.

```
generate api tests for POST /articles          ← natural language, or a prompt:
```

Ready-made prompts - type `/` in chat to see them:

- `/appqe-audit-coverage` - Audit API/UI test coverage against the spec and app, and report prioritized gaps.
- `/appqe-contract-check` - Check existing tests against the current OpenAPI spec for contract drift.
- `/appqe-generate-api-tests` - Generate API tests from the OpenAPI spec into the project's stack.
- `/appqe-investigate` - Investigate a failing API or UI test and deliver a root-cause verdict.

> **Copilot: put `#todo` in your message to get the live task-list panel.** On this build the panel only appears when *you* include `#todo` - a custom agent is not handed the tool otherwise, so without it you get the checklist as plain text. The slash command must come **first** (it is only recognised at the start of the input); `#todo` goes after it, on its own line:
>
> ```
> /appqe-generate-api-tests for /user endpoint
> #todo
> ```
>
> Re-include `#todo` on every gate reply - each message needs its own.
>
> **Bind it so you don't retype it.** Keybindings are user-scoped (a project cannot ship one), so add this once to your *user* `keybindings.json` (Cmd/Ctrl+K Cmd/Ctrl+S -> the `{}` icon) - it opens the run pre-filled in the format above:
>
> ```jsonc
> { "key": "cmd+alt+t", "command": "workbench.action.chat.open",
>   "args": { "query": "/appqe-generate-api-tests for /user endpoint\n#todo", "isPartialQuery": true } }
> ```
>
> The panel also needs `chat.agent.todoList` left at `default` (or set to `chat-input`); `off` hides it. It is `default` out of the box, so this is only worth checking if you have changed it. The panel stays hidden for a list of fewer than three items either way. Claude Code renders the panel natively with none of this.

### 2. In the terminal — you run setup and the read-only checks

**Setup is one command.** `appqe onboard` asks what this project tests, writes
`appqe.yml`, wires the requirement sources already in this repo, maps the
suite's conventions, deploys the
content for GitHub Copilot, and verifies it with `appqe doctor` — then lists
the few things only a person can do. You do not run `sync` afterwards; it
already ran.

Everything else is the same work split into steps, for re-running one on its
own. **None of these starts an agent run:**

```bash
appqe doctor                  # can the guardrails actually run here?
appqe sync                    # re-deploy after editing appqe.yml
appqe sync --prune            # after upgrading appqe: also drops files a release renamed
appqe status <run_id>         # inspect a run the agent drove
appqe list --incomplete       # runs that never finished
appqe summary <run_id>        # re-write a run's summary note
```

`appqe start` / `appqe resume` are the **agent's** commands, not yours. You
drive a run from GitHub Copilot; you inspect it from the terminal.

`appqe --help` lists what you type, grouped by what you are trying to do, and
says which commands the agent drives. There are more behind `appqe --help-all`
for specific jobs (mapping journeys, wiring a requirement source, exporting a
report); you do not need them for a normal run.

## How you use it, day to day

### API testing

The unit is the **endpoint**. A run reads the spec (`specs/openapi.json`),
finds the requirements, plans cases per operation, generates them into
`tests`, runs them, and measures coverage against the spec.

Ask for work in GitHub Copilot like this:

```
generate api tests for POST /articles
audit coverage                       ← what is tested, what is not, in risk order
check contract drift                 ← the running API vs the spec
retest BUG-123                       ← verify a fix, with evidence
```

Checks you can run yourself, any time:

```bash
appqe coverage --kind api --detail    # measured coverage + the gaps, worst first
appqe contract verify                 # probe the running API against the spec
appqe openapi                         # what the spec actually declares
appqe lint tests
```

...and the linter over your test directory, which enforces the assertion
standards as well as the guardrails.

**What "done" means here:** every operation the run touched has a test that
asserts a *documented* status code and shape, error cases included — and the
suite ran, proven by a report appqe parsed itself. Coverage below
80% fails `appqe coverage`.

### Two documents, and they are not the same thing

A run writes two files whose names both sound like "the plan". Telling them
apart saves approving the wrong one, or waiting to approve something that never
asks:

| | What it is | Do you approve it? |
|---|---|---|
| **Run plan** `.appqe/runs/<run_id>-progress.md` | appqe's own steps for this run and what each must prove. Rewritten live as steps settle, and opened when the run starts. | No. It reports what the orchestrator is doing. |
| **Test plan** `.appqe/plans/<run_id>-test-plan.md` | The tests proposed for **your** codebase: what will be covered and how. Written at the planning step. | **Yes** - this is what the plan-approval gate opens. |

### Approval gates

A run pauses for a human at **plan approval** (the **test plan** is written to
`.appqe/plans/<run_id>-test-plan.md` and opened; no tests are generated before it
clears) and **generated-test review** (before tests are final) — and at
**tool_setup**, when it needs requirement sources that are declared but not wired
(wire now / skip this run / never). Two more appear on UI work:
**visual baseline approval** - newly captured screenshots pause for your review
before they become the standard every future run is judged against - and
**instrumentation approval**, the only gate that guards editing the
application's own code (adding test-ids/ARIA roles; the file-by-file, markup-only
diff is what you approve). By default none is auto-approved; set `gates:`
in `appqe.yml` to auto-approve one for an unattended local run. **An auto-approved gate is flagged in the run summary** — it skipped
human review, so its output has no sign-off.

### The run summary

When a run settles, appqe writes `.appqe/reports/<run_id>-summary.md` — the steps
and their findings, the gate decisions (auto-approvals flagged), and the artifacts,
rendered from the recorded state. The agent opens it at the end of a run; review it
before acting on the results. On demand: `appqe summary <run_id>`.

### Test reports (Allure)

For a browsable report of the suite itself - a per-test timeline, the assertion
log, and history across runs - `appqe allure` turns a run's raw **Allure results**
into HTML. It finds the newest `allure-results` directory in the project on its own
(a plain `allure-results/`, or for .NET `bin/Debug/<tfm>/allure-results/`), runs the
Allure CLI, and prints the exact install steps for your OS if that CLI is missing:

```bash
appqe allure           # writes .appqe/reports/allure/index.html
appqe allure --serve   # or open it straight in a browser
```

**Set it up if you have not - it is the report a stakeholder actually reads.** A
run only writes Allure results when the suite has the Allure adapter wired:
`Allure.Xunit` / `Allure.NUnit` (.NET), `allure-pytest` (Python), or the Allure
reporter (Playwright / Jest). It is a few lines of setup and pays off at handover,
where a shareable HTML report beats a terminal log. If `appqe allure` reports no
`allure-results`, add the adapter for your stack, run the suite, then re-run it -
`appqe allure` handles installing the CLI part for you.

## Requirement context (optional, but it deepens the tests)

A spec gives the **shape** of an endpoint; it does not say that a duplicate email
must return 409, or that a wiki page fixed the retry window at 30 seconds. Tests
written from the spec alone are correct and shallow.

**Name a ticket in the request and it is read first.** `/appqe-generate-api-tests
for https://your.atlassian.net/browse/ABC-123` makes reading `ABC-123` step 1 of the
run - named after it, ahead of the discovery log and the spec - because its acceptance
criteria decide what the tests must prove and every later step depends on them. The same
applies to a bare key (`ABC-123`) and to a bug retest. If the ticket cannot be fetched
the run asks you for the criteria rather than planning from the spec and leaving you to
assume your story was read.

Point appqe at the systems that hold the requirements, under `tools:` in `appqe.yml`:

```yaml
tools:
  jira: utilities/jira_client.py               # a script in this repo (the default path), or…
  confluence: mcp:atlassian                    # …an MCP tool, where the host has one and MCP is permitted
```

Each binding is either an MCP tool the host already exposes or a script in this
project. **appqe never calls these systems** — it names the binding and the agent
fetches, so no credential passes through the framework. Any system works, not just
the Atlassian pair — Azure DevOps, GitLab, GitHub, Notion, ServiceNow, Linear, or a
name appqe has never heard of:

```bash
appqe tools list                     # wired / declared / detected, plus the catalog
appqe tools add <name>               # guided setup for any source (aliases work: ADO, gdocs)
appqe scaffold --tool <name>         # dedicated starter (jira, confluence) or the
                                     # generic skeleton with TODO(agent) markers
```

If a run needs sources that are **declared but not wired yet**, it does not fail and
does not guess: appqe raises the `tool_setup` approval gate — wire them now (the
agent does the setup under that approval, and appqe verifies the binding resolves
before continuing), skip for this run, or never (recorded as `binding: skip`, so a
decision made once is not asked again).

Non-secret config (host, project, default space) lives in `appqe.yml`;
credentials go in `env/.env` (git-ignored) — on Atlassian Cloud one
`JIRA_EMAIL` + `JIRA_API_TOKEN` pair covers both products. **You do not have to
wire this before starting a run.** When a generation run reaches a source it
could use but is not configured, it hands the agent the exact setup steps — so
the agent can wire Jira or Confluence in place if the requirements need it, or
build from the spec alone and say so. `appqe doctor` reports any binding that
does not resolve.

## Project conventions (what generated tests build on)

appqe assumes nothing about this project's structure. `appqe conventions
discover` records the suite's own seams - client factory, test-data builder,
auth helper, page objects, selector policy - into `.appqe/conventions.yml`:
project-owned, hand-editable, committed, and verified against the code on disk
(`appqe doctor` flags entries that rot). Generation runs receive the map
directly and the `appqe-project-conventions` skill renders it for the agent;
without a map, the agent is instructed to read existing tests first rather than
assume. For the richer pass, `appqe conventions discover --deep` prints a
worksheet your coding agent answers from the code; `appqe conventions accept`
verifies every claim before it enters the map.


## The checks

| Command | What it enforces |
|---|---|
| `dotnet test` | the API suite itself |
| `appqe lint tests` | secrets, production URLs, disabled TLS, ambiguous status assertions |
| `appqe lint tests --strict` | the above plus the assertion standards |
| `appqe coverage --kind api --detail` | measured endpoint coverage, gaps in risk order |
| `appqe coverage --kind api --check-baseline` | fails on coverage regression (use in CI) |
| `appqe contract verify` | drift between the spec and the running API |

Every number here is **measured** — from the spec and your
test sources for API coverage. None of
them is a figure someone types in. On an existing
codebase, gate CI on `appqe coverage --kind api --check-baseline` rather than
the absolute threshold: an absolute gate is red on day one and gets switched
off, which enforces nothing. Move the baseline deliberately with
`--accept-baseline` and commit the diff.

## Institutional memory

`.github/okf/findings/` carries what previous runs learned — auth quirks, flaky
causes, places the spec and the implementation disagree. It is an Open Knowledge
Format bundle: one markdown doc per finding, filed under its area, plus a
generated `index.md`.

```bash
appqe discovery                  # the rules index
appqe discovery add --area <endpoint> --finding <what> --cause <why> --rule <next time>
appqe discovery promote <slug>   # make a repeated rule permanent
```

The bundle is committed, so the team shares one memory: `sync` wires a merge that
adds up sightings across branches rather than picking one, which means two people
who independently hit the same thing confirm it between them. (`index.md` is
generated and git-ignored - never edit or hand-merge it.)

Recording the same finding twice bumps its `seen_count` rather than duplicating
it, and that count decides what a run is told. Seen once, it is a hypothesis and
stays out of the session. Seen twice, it becomes a rule, and the rules in force
are injected at the start of every run automatically. That is what keeps the
read cost flat as the project accumulates knowledge.

**This log is engagement-local.** Treat its contents as client-confidential:
findings name hosts, endpoints, auth behaviour and defect ids. Do not copy it
into another project.

## Bringing your own skills, instructions, and extensions

The framework ships a baseline; **your project extends it without forking** - this is
part of the ~30% you own. Two of these are **prose** the agent reads (skills,
instructions); the third is **code** that adds a capability appqe never shipped.

- **Project skills.** Author your own skill package - a `SKILL.md` (plus any
  `references/`, `scripts/`, `templates/`) - under any name that is **not** `appqe-*`,
  in the skills directory appqe deploys to. Sync never overwrites it, and the agent
  loads it like a shipped skill when it fits the task:

  ```bash
  appqe scaffold --skill payments-domain   # stubs the SKILL.md (prints the path)
  appqe inventory                          # lists shipped + your project skills
  ```

- **Project instructions (prose).** Put team conventions - naming, which endpoints
  matter, what "done" means here - in the `appqe:custom` block the agent contract ships
  ready for them (or one in this file, or your `AGENTS.md`). They
  **survive every sync**, and the agent honors them - they tailor conventions, never
  relaxing a gate, a guardrail, or an evidence requirement.

- **Project extensions (code).** For a *new* capability the framework doesn't ship - a
  new run mode, test stack, or agent host - register a Python **entry point** in your
  `pyproject.toml`. Instructions above change *how* the agent works; an extension adds a
  *new kind* of work:

  ```toml
  [project.entry-points."appqe.workflows"]
  security_scan = "acme.qe:security_workflow"   # a new run mode, no fork
  ```

  `appqe.profiles` adds a test stack, `appqe.platforms` a host. Run `appqe capabilities`
  to list what is registered.

## What appqe manages here

Files carrying `<!-- appqe:managed vX.Y.Z -->` are generated — edit
`appqe.yml` and re-run `appqe sync`, not the files themselves. Local edits are
overwritten. `appqe inventory` lists them and flags version drift.

Everything else in the repo — your tests, fixtures, CI — is yours.

## Handover

Before the engagement closes:

1. **Deliver the CLI through a channel the client controls, and set
   `install_command` in `appqe.yml` to the command that uses it.** This is the one
   step that blocks everything else: the guardrail hooks fail closed, so an
   engineer who cannot install the CLI has every agent tool call refused, with no
   fix available in this document. Publish the versioned wheel to the artifact
   registry the team already uses, or vendor it in the repo (`uv build` produces
   one; appqe has zero runtime dependencies, so the single file installs
   air-gapped). Then re-run `appqe sync` so this page prints that command.
2. **Verify it the way they will experience it:** in a fresh clone, with only
   the credentials the receiving team has, run the `install_command` and then
   `appqe doctor`.
3. `appqe coverage --kind api --detail` - hand over the measured number
   **and** the named gaps, not a percentage.
4. `appqe discovery` - walk the receiving team through the rules in force.
5. Decide who owns `appqe.yml` — particularly `security.allowed_hosts` and
   `allow_prod`, which are the guardrails against touching production, and who may
   move the coverage baseline (`--accept-baseline`), which is the quality ratchet.
6. Agree who upgrades appqe. The version is pinned per project by whatever
   `install_command` names; `appqe doctor` reports the version the deployed content
   was generated by, so a drift between the two is visible.
7. `appqe handover` - write the close-out report (`QE-CLOSE-OUT.md`). Run state and
   telemetry live under `.git/appqe/`, which does not survive a fresh clone, so this
   is the only form in which the engagement's record transfers: the gated coverage
   position, the run history including what did not finish, and who inherits the
   gates. Review it before sharing - it describes your engagement.
8. If appqe is being removed rather than handed on: `appqe remove` un-wires the
   project (content, hook entries, the `.gitignore` block) and `appqe remove --purge`
   also deletes run state, `appqe.yml` and the coverage baseline. Both print exactly
   what will go and ask first; `--dry-run` shows the plan and changes nothing. Your
   tests are never touched. Run `appqe handover` **before** `--purge`, because the
   report is rendered from the state it deletes.
