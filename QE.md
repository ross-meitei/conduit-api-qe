# QE setup — conduit-api-qe

How the agentic QE workflow in this repo is set up, how to use it, and what to
do with it when the engagement ends. Written for people; everything else appqe
deploys is written for the agent.

Generated by appqe. Re-run `appqe sync` after changing `appqe.yml`.

## Prerequisites

The guardrails shell out to the `appqe` CLI, and they **fail closed** — if it is
not installed, tool calls are blocked rather than silently unguarded. Install it
before working in this repo:

```bash
uv tool install appqe            # or: pipx install appqe
appqe --version                  # expect: 0.1.0
appqe doctor                     # verifies wiring in this project
```

`appqe doctor` is the one command worth running after any setup change. It
reports whether the CLI resolves, the config and spec load, the hooks are wired
for this host, and whether a coverage baseline exists.

## Using it

Select the **appqe** agent in GitHub Copilot, then describe the QE task.
The agent drives a phased run through the orchestrator — it does not improvise a
workflow — and stops at approval gates.

```bash
appqe start "generate api tests for POST /articles"   # -> run_id + first batch
appqe status <run_id>                                 # where a run got to
appqe list --incomplete                               # runs that never finished
```

> **Copilot: type `#todo` to get the live task-list panel.** On this build the panel only appears when *you* put `#todo` in your message - a custom agent is not handed the tool otherwise, so without it you get the checklist as plain text. Prefix the run and re-include it on gate replies:
>
> ```
> #todo /appqe-generate-api-tests for /user
> ```
>
> Requires `chat.tools.todos.showWidget: true` at **workspace** scope (a multi-root workspace ignores a per-folder `.vscode/settings.json`). Claude Code renders the panel natively with none of this.

Ready-made requests are available as prompts:

- `/appqe-audit-coverage` - Audit API/UI test coverage against the spec and app, and report prioritized gaps.
- `/appqe-contract-check` - Check existing tests against the current OpenAPI spec for contract drift.
- `/appqe-generate-api-tests` - Generate API tests from the OpenAPI spec into the project's stack.
- `/appqe-investigate` - Investigate a failing API or UI test and deliver a root-cause verdict.

### Approval gates

Runs pause for a human at:

- **plan approval** — the test plan is written to `.appqe/plans/<run_id>-test-plan.md`
  and opened for review. No tests are generated before this clears.
- **generated-test review** — before generated tests are considered final.

Neither is auto-approved. Gates are configured under `gates:` in `appqe.yml`.

## Requirement context (optional, but it deepens the tests)

A spec gives the **shape** of an endpoint; it does not say that a duplicate email
must return 409, or that a wiki page fixed the retry window at 30 seconds. Tests
written from the spec alone are correct and shallow. Point appqe at the systems
that hold the requirements, under `tools:` in `appqe.yml`:

```yaml
tools:
  jira: mcp:atlassian/getJiraIssue        # an MCP tool the host already has, or…
  confluence: utilities/confluence_client.py   # …a script in this repo
```

Each binding is either an MCP tool the host already exposes or a script in this
project. **appqe never calls these systems** — it names the binding and the agent
fetches, so no credential passes through the framework. Jira and Confluence ship
starter clients:

```bash
appqe scaffold --tool jira           # writes utilities/jira_client.py
appqe scaffold --tool confluence     # writes utilities/confluence_client.py
```

Non-secret config (host, project, default space) lives in `appqe.yml`;
credentials go in `env/.env` (git-ignored) — on Atlassian Cloud one
`JIRA_EMAIL` + `JIRA_API_TOKEN` pair covers both products. **You do not have to
wire this before starting a run.** When a generation run reaches a source it
could use but is not configured, it hands the agent the exact setup steps — so
the agent can wire Jira or Confluence in place if the requirements need it, or
build from the spec alone and say so. `appqe doctor` reports any binding that
does not resolve.

## The checks

| Command | What it enforces |
|---|---|
| `dotnet test` | the suite itself |
| `appqe lint tests/api` | secrets, production URLs, disabled TLS, ambiguous status assertions |
| `appqe lint tests/api --strict` | the above plus the assertion standards |
| `appqe coverage --kind api --detail` | measured endpoint coverage, gaps in risk order |
| `appqe coverage --kind api --check-baseline` | fails on coverage regression (use in CI) |
| `appqe contract verify` | drift between the spec and the running API |

Coverage is **measured** from the spec and your test sources — it is never a
number someone types in. On an existing codebase gate CI on `--check-baseline`
rather than the absolute threshold: an absolute gate is red on day one and gets
switched off, which enforces nothing. Move the baseline deliberately with
`appqe coverage --kind api --accept-baseline` and commit the diff.

## Institutional memory

`.github/discovery.md` carries what previous runs learned — auth quirks, flaky
causes, places the spec and the implementation disagree. It is read at the start
of every run and injected into the session automatically.

```bash
appqe discovery                  # the rules index
appqe discovery add --area <endpoint> --finding <what> --cause <why> --rule <next time>
```

**This log is engagement-local.** Treat its contents as client-confidential:
findings name hosts, endpoints, auth behaviour and defect ids. Do not copy it
into another project.

## What appqe manages here

Files carrying `<!-- appqe:managed vX.Y.Z -->` are generated — edit
`appqe.yml` and re-run `appqe sync`, not the files themselves. Local edits are
overwritten. `appqe inventory` lists them and flags version drift.

Everything else in the repo — your tests, fixtures, CI — is yours.

## Handover

Before the engagement closes:

1. `appqe doctor` — confirm a fresh clone can run the guardrails.
2. `appqe coverage --kind api --detail` — hand over the measured number **and**
   the named gaps, not a percentage.
3. `appqe discovery` — walk the receiving team through the rules in force.
4. Confirm the CLI install step above is in their onboarding docs; without it
   the hooks block tool calls on a fresh clone.
5. Decide who owns `appqe.yml` — particularly `security.allowed_hosts` and
   `allow_prod`, which are the guardrails against touching production.
